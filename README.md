# UI-автотесты на Selenium: Vesperfin

Учебный фреймворк для UI-автотестов. Приложение под тестом — **https://vesperfin.com**, сайт финансовой онлайн-школы.

Задача: реализовать [тест-кейсы из Confluence](https://testplay2.atlassian.net/wiki/x/AQC9GQ) на этом фреймворке. Кейсы короткие, по 1–3 шага: смысл не в хитрых сценариях, а в объёме. За 60 тестов рука привыкает искать локаторы, ждать элементы и писать внятные проверки — вместо того чтобы гуглить каждую строчку.

Что делать по шагам, как заводить сабтаски и оформлять сдачу — в [задаче Jira](https://testplay2.atlassian.net). Здесь только про сам фреймворк.

## Как начать

1. **Форкните** этот репозиторий в свой проект и клонируйте форк. Работаете только в нём.
2. Поднимите окружение:

```bash
python3 -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp config/.env.example config/.env.prod
```

3. Убедитесь, что примеры проходят:

```bash
pytest -v
```

Должно быть `2 passed` — это кейсы C-01 и C-06, написанные как образец стиля. Остальные пишете вы.

Нужен установленный Chrome. Драйвер Selenium скачает сам.

## Запуск

```bash
pytest                                # весь набор, окно браузера открывается
pytest --headless                     # без окна
pytest -m smoke                       # только smoke-кейсы
pytest --viewport=mobile -m mobile    # кейсы мобильной версии
pytest tests/test_navigation.py -v    # один файл
pytest tests/test_navigation.py::TestNavigation::test_home_page_opens   # один тест
pytest -n 4                           # параллельно, не больше 4 воркеров
```

Ключи: `--browser` (chrome/firefox), `--headless`, `--viewport` (mobile/tablet/desktop), `--env`.

## Отчёт Allure

```bash
pytest --headless
allure serve allure-results
```

Нужен Allure Commandline и Java. При падении теста в отчёт кладутся скриншот, URL и лог консоли браузера — по ним разбирайте падения, а не «запущу ещё раз и посмотрю».

Скриншот отчёта прикладывается к сабтаске при сдаче.

## Проверка стиля

```bash
ruff check .
ruff format .
```

`ruff check .` должен проходить чисто — это часть требований к сдаче.

## Что в проекте

```
├── config/
│   ├── environments.py     # окружение на pydantic-settings: базовый URL и таймаут
│   └── .env.example        # шаблон; настоящие .env.* в git не попадают
├── pages/
│   ├── base_page.py        # ожидания, действия, работа с хранилищем, Allure-вложения
│   ├── application.py      # фасад: единая точка входа ко всем страницам
│   ├── home_page.py        # образец Page Object — по нему пишете остальные
│   └── contacts_page.py
├── utils/
│   ├── assertions.py       # проверки с внятными сообщениями
│   ├── parsing.py          # разбор данных, которые сайт отдаёт для человека
│   └── http.py             # проверка доступности файлов без браузера
├── tests/
│   └── test_navigation.py  # блок 1: реализованы C-01 и C-06, остальное за вами
├── conftest.py             # опции запуска, фикстуры драйвера и окружения, артефакты падений
└── pyproject.toml          # настройки pytest, маркеры, ruff
```

Что добавляете вы: Page Object на каждую страницу и сквозной компонент из кейсов (каталог, страница курса, вопросы, шапка, подвал, cookie-баннер, форма), их регистрацию в `application.py`, хранилище тестовых данных и сами тесты.

Ожидания и работа с браузером живут в `BasePage`. Нужного ожидания нет — добавляете его туда, а не костыль в тест.

## Требования к реализации

Действуют для всех кейсов. Нарушение любого — возврат на доработку.

**Структура.** Тесты раскладываются по файлам согласно полю «Автотест» в кейсе. Классы `Test*`, методы `test_*`. Один кейс — один тест-метод. Один блок кейсов — одна сабтаска, одна ветка, один PR.

**Слои.**
- Локаторы — константами в Page Object. В тестах локаторов нет.
- Действия и получение данных со страницы — методы Page Object. `driver.find_element` в тесте — возврат.
- Проверки — функции из `utils/assertions.py` или своего `assertions`-модуля рядом со страницей. Внутри Page Object `assert` не пишем.
- Новую страницу регистрируем в `pages/application.py`, тест получает только фикстуру `app`.

**Ожидания.** Только явные, из `BasePage`. `time.sleep` запрещён. Нужного ожидания нет — добавляете его в `BasePage`, а не костыль в тест.

**Ассерты.** Каждый с сообщением: что проверяли, что ожидали, что получили. `assert x` без сообщения — возврат.

**Allure.** У теста `@allure.title` с названием кейса (включая его ID), у класса `@allure.feature`. Каждый шаг из кейса — отдельный `with allure.step(...)`.

**Маркеры.** Кейсы с приоритетом Smoke помечаются `@pytest.mark.smoke`, остальные — `@pytest.mark.regression`. Кейсы мобильной версии дополнительно `@pytest.mark.mobile`.

**Параметризация.** Кейсы, помеченные как параметризованные, реализуются одним тест-методом с `@pytest.mark.parametrize` и осмысленными `ids`. Копипаста вместо параметризации — возврат.

**Тестовые данные.** Конкретные значения абстрактных данных из кейсов (URL, ожидаемые тексты, наборы невалидных email) выносятся из тела теста: одиночное значение — в константу модуля, наборы и всё, что переиспользуется между файлами, — в отдельный модуль тестовых данных. Структуру заводите сами.

**Изоляция.** Каждый тест сам приводит систему в нужное состояние. Опираться на действия предыдущего теста нельзя.

**Cookie-баннер.** Он висит поверх страницы и перехватывает клики в нижней части экрана. Если клик не проходит — разберитесь, кто его перехватывает, и объясните решение в сабтаске.

## 🚨 Правила работы с боевым сайтом

Читать обязательно. Нарушение — работа не зачтена.

1. **Не отправляем формы.** За формой обратной связи стоит CRM и живой отдел продаж: каждая отправка — это лид, которому будут звонить. Кейсы блока «Формы» проверяют поведение **до** отправки: браузерную валидацию, состояние полей и флажка. Поэтому в них нет ни одного успешного сабмита.
2. **Не трогаем оплату.** Кнопки, ведущие на платёжный шлюз, не нажимаем.
3. **Никакой нагрузки.** Не больше 4 воркеров, никаких циклов «прогоню сто раз».
4. **Не коммитим секреты.** Любые креды — только в `.env`, который в `.gitignore`.
5. Если тест по недосмотру отправил заявку — сразу напишите ментору. Это не наказуемо, наказуемо молчание.

## Definition of Done для каждой сабтаски

- [ ] Тест-кейсы блока заведены в Zephyr и прилинкованы к сабтаске.
- [ ] Тесты запускаются с чистого клона по инструкции из этого README.
- [ ] Прогон **дважды подряд зелёный**. Один зелёный прогон ничего не доказывает.
- [ ] Тесты **не зависят от порядка** и проходят по одному.
- [ ] **Ни одного** `time.sleep`. Ожидания — явные и по условию.
- [ ] Взаимодействие со страницей — только через Page Object. В тесте нет `driver.find_element`.
- [ ] Ассерты с сообщением: по тексту падения понятно, что сломалось, без чтения кода.
- [ ] Данные, которые могут измениться вместе с сайтом, вынесены из тела теста.
- [ ] Параметризованные кейсы реализованы через `parametrize`, а не копипастой.
- [ ] `ruff check .` — чисто.
- [ ] В коммит не попали `.env`, `allure-results/`, `venv/`, `__pycache__/`, `.idea/`, `.DS_Store`.
- [ ] В комментарии к сабтаске: ссылка на PR и скриншот прогона Allure.

## Как оценивается работа

По убыванию важности:

1. **Тест ловит регресс?** Сломайте проверяемое поведение через DevTools — тест должен покраснеть. Тест, который не может упасть, хуже отсутствия теста: он врёт.
2. **Тест стабилен?** Переживает медленную сеть, повторный и параллельный прогон.
3. **Падение диагностируемо?** По Allure видно шаг, скриншот и URL — без «сейчас воспроизведу локально».
4. **Архитектура.** Логика в нужном слое, дублирования нет, новый кейс добавляется в три строчки.
5. **Читаемость.** Тест читается как сценарий, а не как код.

## Частые ошибки, за которые вернут PR

1. Проверка «элемент есть в DOM» вместо «элемент видим и содержит нужное».
2. `assert len(cards) > 0` без сообщения: непонятно, что проверяли и что получили.
3. Один тест на десять проверок сразу. Один кейс — один тест.
4. `sleep(2)` после клика.
5. Копипаста вместо параметризации.
6. Локатор вида `div > div > div:nth-child(3)` или по классу с хешем — умрёт на первом релизе.
7. Подгонка ожидаемого результата под фактическое поведение сайта вместо вопроса ментору.
8. Отправка формы на боевом сайте.

## Правила игры

- Локаторы ищете сами через DevTools. Готовых селекторов в кейсах нет намеренно — кроме тех, что уже в коде.
- Кейсы сверены с реальным поведением сайта. Если факт разошёлся с ожидаемым результатом — это находка: заводите баг и пишете о нём в сабтаске, а не переписываете ожидание под факт.
- ИИ как справочник — можно. ИИ как автор PR — нет. На ревью спросят «почему здесь так» по любой строке; не сможете объяснить — работа не зачтена.
- Застряли больше чем на час — пишите. Это тренировка, а не экзамен.
